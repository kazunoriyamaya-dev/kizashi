# 運用 - ロールバック

## 1. ロールバック可能な範囲

| 種類                | 方法                               | 所要時間 |
| ------------------- | ---------------------------------- | -------- |
| Vercel デプロイ     | Dashboard で前バージョンを Promote | 1-2分    |
| Supabase Migration  | 手動逆 migration を流す            | 5-30分   |
| Stripe Webhook 設定 | Dashboard で元の URL に戻す        | 1分      |

## 2. Vercel デプロイのロールバック

### 2.1 即時手順

1. Vercel Dashboard → Project → Deployments
2. 直前の正常デプロイを選択
3. 右上「Promote to Production」を押下
4. 数秒で本番が切り替わる
5. **DNS / CDN キャッシュは即時反映**

### 2.2 注意事項

- **DB migration を含むデプロイ**は単純な Promote だけでは戻せない
  - コード: ロールバック可
  - DB schema: 既に進んでいるため別途逆 migration が必要
- ロールバック前に Slack で担当者全員に通知

## 3. Supabase Migration のロールバック

### 3.1 破壊的でない migration の場合

```bash
# 該当 migration を逆向きに書く (down migration)
cat > supabase/migrations/$(date +%Y%m%d%H%M%S)_rollback_xxx.sql <<EOF
-- 例: alter table ... drop column ...
alter table public.foo drop column if exists new_col;
EOF

supabase db push
```

### 3.2 破壊的 migration の場合 (column 削除等)

1. 上記のリハーサル環境で復旧テスト
2. メンテナンスモード（Vercel で 503 を返す中間ページ）に切替
3. PITR / pg_dump からデータを復元
4. アプリも対応バージョンに Promote

### 3.3 RPC / RLS のロールバック

- RPC: `create or replace function ...` で旧版を再定義
- RLS: 該当 policy を `drop policy ...` → 旧 policy を再作成

## 4. Stripe Webhook の切り戻し

1. Stripe Dashboard → Developers → Webhooks
2. 該当 endpoint を **Disable** （Delete はしない）
3. 旧 endpoint があれば Enable
4. 旧 endpoint の signing secret を Vercel 環境変数 `STRIPE_WEBHOOK_SECRET` に反映
5. アプリを再デプロイ

## 5. ロールバック判断基準

以下のいずれかが該当する場合、即時ロールバックを検討:

- [ ] **5xx エラー率** が直近の 1% を超える
- [ ] **予約成立率** が直近の 30% を下回る
- [ ] **チケット購入の成功率** が 80% を下回る
- [ ] **個人情報漏洩** の疑い (要即時 + 関係者通知)
- [ ] **二重課金 / 二重チケット付与** の発生

## 6. ポストモーテム

ロールバック実施後 48 時間以内に:

1. ロールバック起因の障害サマリーを `docs/incidents/YYYY-MM-DD-xxx.md` に記録
2. 一次対応者 (KUGEDOU 山谷氏): 影響範囲・タイムライン・原因仮説
3. Root Cause Analysis: 5 Whys
4. 再発防止策 (テストケース追加 / 監視追加 / プロセス変更)

## 7. メンテナンス時間枠

- 計画ロールバック: 火曜 02:00-04:00 JST (利用者が少ない時間帯)
- 緊急時: 24/7 対応 (一次: KUGEDOU 代表 山谷氏)
